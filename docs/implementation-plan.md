## Межі робіт

Перший результат — структурований проєкт зі збереженою поведінкою одного кондиціонера. Другий — опційне узгоджене керування кількома кондиціонерами зі спільним енергетичним бюджетом.

Зберігаємо один config entry на кондиціонер. Енергетична група має стабільний ідентифікатор і єдине джерело конфігурації спільних датчиків та обмежень. Конкретний спосіб представлення групи в HA фіксуємо на етапі 5 після перевірки підтримуваного API. Пристрої не об’єднуються автоматично за збігом датчиків.

Кожен пункт нижче — окрема перевірювана зміна. Після етапу фіксуємо виконані роботи, результати перевірок і відхилення в цьому документі. До наступного етапу переходимо, коли виконані критерії готовності. Випуски й розгортання плануються окремо від локальної реалізації.

- Одноразове порівняння 2 000 послідовних оцінювань зі станом після етапу 2 не виявило змін жодного публічного поля або Store v1. Цей експеримент доповнює тести й не є доказом для всіх можливих входів.
- Наступний етап — окремий виконавець команд і runtime пристрою. Шаблон GitHub CI залишається неактивним.

## Результат етапу 4 — 2026-10-15

- Виділено `runtime/device.py`: стан пристрою, потреба, політика, фактичні таймери, намір керування, режим і ручне блокування. Модуль не імпортує HA.
- Виділено `runtime/commands.py`: одна задача на пристрій, відправлення, обмеження повторів, timeout, контексти, очікувані відповіді та скасування.
- Додано `CommandAttempt`: відправлення, результат сервісного виклику й підтвердження новим станом відстежуються незалежно. Timeout/скасування не змінюють фактичні таймери.
- Координатор залишає підписки HA, цикл оцінювання, публікацію, збереження й життєвий цикл. Після shutdown ігноруються пізні події.
- Збережено Store v1, зовнішні ключі сутностей, пороги, інтервали повторів і правила ручних змін. Sensor та diagnostics читають стан із runtime.
- Додано регресії часткового підтвердження, пізнього off після timeout, ручної зміни під час команди, скасування при зміні режиму/unload і сумісності diagnostics. Строгий mypy розширено до 8 файлів.
- Контрольна точка А: структура готова до подальшого розширення. Перевірка в observation на реальній установці залишається окремим кроком; групове керування ще не реалізоване.
- Перевірки: 165 unit-тестів на Windows/Python 3.11 і Linux/Python 3.14.2; 18 HA-тестів на HA 2026.10.1; Ruff, mypy, compileall, pip check і git diff --check пройшли. GitHub workflow вимкнений.

## Результат етапу 5 — 2026-10-15

- Прийнято [ADR 001](adr-001-energy-groups.md): окремий HA Store для груп, один config entry на кондиціонер, явне членство, контракт загального лічильника та спільної політики.
- Додано незмінні GroupSources, GroupPolicy, MemberPolicy, GroupConfig, Membership, UnresolvedReservation і GroupRegistry. Група має UUID; пристрій — стабільний device_id. Подвійне членство заборонене.
- Config v1 → v2 додає device_id зі старого entry_id; нові entries отримують UUID. Режими, options, entity IDs і Store пристрою v1 збережені. Метадані ID виключено із сигнатур політики.
- GroupRepository серіалізує зміни та публікує новий реєстр тільки після успішного збереження. Пошкоджений/майбутній формат не перезаписується порожніми даними. Неврегульовані резерви зберігаються після reload і блокують вихід/перенесення/видалення.
- readiness описує неповну конфігурацію та відсутніх учасників; configured не є дозволом старту. Модель поки не підключена до чинного командного шляху. UI створення/вибору груп залишається етапом 8, allocator — етапом 6, реальні групові команди — етапом 7.
- Перевірки: 176 unit-тестів на Windows/Python 3.11 і Linux/Python 3.14.2; 25 HA-тестів на HA 2026.10.1. Ruff, mypy (11 файлів), pip check, compileall і git diff --check пройшли. GitHub workflow залишається вимкненим.
