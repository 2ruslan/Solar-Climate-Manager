# Демо-стратегія 0.2.2

Версія 0.2.0 обчислює енергетичні рішення й симулює цикли кондиціонера. У коді немає викликів сервісів кондиціонера чи інвертора. `control_allowed` завжди `false`. Віртуальний кондиціонер не змінює реальне споживання, температуру чи генерацію.

## Підключення джерел

Оновіть інтеграцію у HACS, перезапустіть HA, відкрийте **Пристрої та служби → Solar Climate Manager → Налаштувати** біля запису кондиціонера. Наявні вибрані джерела зберігаються. Форма містить нові поля; збереження перезавантажує запис.

| Джерело | Призначення |
|---|---|
| Температура та climate | Температурна потреба й виявлення зовнішніх змін |
| Фактична PV-потужність | Поточна виміряна потужність, W/kW |
| Загальне споживання | Навантаження у W/kW; включення заряджання батареї задається окремим перемикачем |
| Окрема потужність заряджання батареї | Необов’язковий датчик додатної потужності заряду W/kW; за відсутності заряд визначається зі знакової потужності батареї |
| SOC | Заряд акумулятора, % |
| Потужність батареї | Знакова потужність заряду/розряду, W/kW |
| Потужність мережі | Знакова потужність імпорту/експорту, W/kW |
| Наявність мережі | Бінарний сенсор; можна інвертувати значення ON |
| Прогноз зараз/+30/+60 | Потужність на відповідні моменти, W/kW |
| Потужність кондиціонера | Необов’язковий окремий датчик для віднімання його фактичного споживання з навантаження |
| Розклад | Необов’язковий HA `schedule`: ON дозволяє демо, OFF/недоступно забороняє |

Поля енергетичних сутностей необов’язкові у формі, щоб старі записи продовжували працювати. **Для енергетичного старту всі основні джерела потрібні**. Відсутність, недоступність, застарілі повідомлення та некоректні одиниці блокують старт. За умовчанням потрібен і прогноз; його вимогу можна вимкнути, щоб перевіряти стратегію лише за фактичними даними. SOC, навантаження та потужність перевіряються за `power_max_data_age`; для наявності мережі є окремий ліміт, типово 24 години. Якщо бінарний сенсор не повідомляє стан повторно, налаштуйте його heartbeat або відповідний ліміт, а не вважайте застарілий ON гарантією мережі.

Перевірте знаки датчиків: параметри «Додатна потужність батареї означає» та «Додатна потужність мережі означає» налаштовуються незалежно. Діагностичні значення нормалізовані: **додатна батарея = розряд; додатна мережа = імпорт**. Для датчиків окремого імпорту/експорту або заряду/розряду потрібно спочатку створити знаковий template sensor; один модульний показ не відображає обидва напрями.

## Параметри й типові значення

У 0.2.1 додано перемикач **«Загальне споживання включає заряджання батареї»**. За умовчанням він вимкнений для сумісності зі старою конфігурацією. Якщо ваш загальний показник містить заряджання, увімкніть його та за наявності виберіть окремий датчик зарядної потужності. Наприклад: загальне споживання 1600 W, заряджання 1000 W → споживання будинку 600 W. У стратегії зарядний бюджет додається потім лише один раз відповідно до пріоритету SOC.

Окремий зарядний сенсор має бути потужністю, а не накопиченою енергією, і показувати нуль за відсутності заряджання. Якщо він не вибраний, заряд = `max(0, −нормалізована потужність батареї)`. Розряд батареї не віднімається від загального навантаження. Недоступний вибраний зарядний сенсор або заряд більший за загальне споживання робить розрахунок недоступним і блокує демо-старт. Знаковий датчик батареї залишається потрібним для захисту від розряду.

Діагностика окремо показує сире загальне споживання, потужність окремого зарядного сенсора та розраховане споживання будинку без заряджання. Існуючий entity ID загального показника зберігається; його назва оновлюється.

| Параметр | Типове значення |
|---|---|
| Оцінена потужність кондиціонера | 900 W |
| Резерв потужності / енергетичний гістерезис | 300 W / 150 W |
| Мінімальний / критичний / резервний SOC | 85% / 20% / 90% |
| Пріоритет заряджання | Увімкнений; бюджет не менше 500 W нижче резервного SOC |
| Допустимий розряд батареї | 100 W |
| Дозволити імпорт із мережі | Вимкнено; ліміт 300 W |
| Підтвердження надлишку | 600 s |
| Підтвердження дефіциту / відсутності мережі | Окремо по 600 s |
| Мінімальна робота / пауза | По 600 s |
| Стабілізація після старту | 180 s |
| Підтвердження перевищення імпорту/розряду | 60 s після стабілізації |
| Пробний старт за прогнозом при обмеженні PV | Вимкнено |
| Пауза після зовнішніх змін | Увімкнено, до кінця локальної доби HA |

Пороги мають задовольняти `critical SOC < minimum SOC ≤ reserve SOC`. Ці типові значення є початковою конфігурацією для демо, а не калібруванням вашого обладнання.

## Як приймається рішення

1. Температурний термостат формує незалежну потребу.
2. Вимкнений перемикач, ручна пауза чи заборона розкладу скидають віртуальну роботу. Реальний кондиціонер залишається як є.
3. Критичний SOC, недоступні критичні дані, SOC нижче мінімуму або розряд нижче бажаного резерву зупиняють віртуальний цикл без очікування мінімального часу роботи.
4. `Сонячний бюджет = PV − базове навантаження − інші віртуальні кондиціонери − оцінка цього кондиціонера − резерв − бюджет заряджання`. Для старту бюджет має бути не менше гістерезису; для продовження допускається зниження до від’ємного гістерезису.
5. Якщо навантаження включає реальний кондиціонер, з нього віднімається окремо виміряна потужність AC. Без датчика використовується ручна оцінка лише при `hvac_action: heating/cooling`; за невідомої активності нічого не віднімається. **Віртуальна робота ніколи не віднімається з реального навантаження.** Неправильна оцінка реального AC може спотворювати бюджет; окремий датчик точніший.
6. Нижче резервного SOC та за пріоритету заряджання бюджет заряджання є більшим із заданого резерву заряджання й поточного виміряного заряду. За вимкненого пріоритету цей бюджет дорівнює нулю; фактичні ліміти розряду все одно діють.
7. Прогнозний бюджет обчислюється за мінімальною прогнозованою потужністю. Він не підміняє фактичну PV-потужність.
8. Достатні умови мають тривати безперервно заданий час; будь-який розрив скидає підтвердження. Мінімальна пауза діє додатково. Діагностика показує залишок часу, якщо старт/зупинка вже очікуються; `unknown` означає, що активного відліку немає.
9. За дозволеного імпорту можна стартувати в межах ліміту прогнозованого додаткового імпорту; відсутність мережі вимикає цей шлях. Наявність мережі сама по собі не дозволяє довільне споживання батареї.
10. Під час віртуального циклу контролюються фактичний імпорт/розряд, енергетичний дефіцит і температура. Для зупинки через відключення мають сплинути **обидва незалежні таймери**: відсутності мережі та нестачі потужності. Це захисна зупинка, яка обходить мінімальний час роботи. Звичайний дефіцит за наявної мережі враховує мінімальну роботу.

Пробний старт за прогнозом дозволений лише при SOC не нижче бажаного резерву, достатньому прогнозі та допустимих фактичних імпорті/розряді. Якщо після стабілізації фактичний бюджет не підтверджується, віртуальний цикл зупиняється. **Демо фізично не підвищує навантаження, тому не може перевірити реальний вихід інвертора з curtailment.** Залишайте пробні старти вимкненими для початкового спостереження.

## Прогноз: три сенсори, останні доступні значення

Виберіть прогноз потужності зараз, через 30 хвилин і через 1 годину у W/kW. Стратегія використовує мінімум цих трьох значень для прогнозного бюджету. Це наближення, яке може пропускати провали між точками; підтвердження надлишку й захисні рішення спираються також на фактичні вимірювання.

Вік прогнозу не блокує його використання. Читається останнє доступне числове значення вибраного сенсора незалежно від часу повідомлення HA. Стан unavailable/unknown, некоректні одиниці, від’ємні чи нескінченні значення не підміняються останнім числом. Якщо прогноз обов’язковий, такі дані блокують прогнозний дозвіл. Час оновлення, детальне джерело, назви атрибутів, одиниці деталізації та горизонт прибрано з налаштувань.

Прогноз залишається очікуванням, а не фактично доступною енергією. Фактичні PV, навантаження, SOC і потужність батареї/мережі продовжують проходити перевірку актуальності. Старі збережені параметри деталізації й віку прогнозу ігноруються; наявні три джерела зберігаються, після збереження Options Flow застарілі поля з options видаляються.

## Ручний пріоритет, перезапуск і кілька кондиціонерів

Зміни HVAC mode, цільової температури, fan/preset/swing та відомих climate-атрибутів quiet/xtra_fan призупиняють демо до кінця поточної календарної дати в timezone HA. Зміни `current_temperature` та `hvac_action` не є ручним втручанням; тимчасові unknown/unavailable не оголошуються ручними командами. У демо власних кліматичних команд немає, тому всі спостережені зміни керованих атрибутів є зовнішніми. Відрізнити пульт від іншої автоматизації достовірно не можна. Quiet, що існує лише окремою switch-сутністю, наразі не відстежується.

Ручна дата й віртуальний стан зберігаються через HA Store. Після restart відновлюються термостат, ручна пауза та моменти віртуального старту/зупинки для мінімальних циклів. Безперервні підтвердження надлишку, дефіциту, відключення й небажаної потужності починаються заново, бо під час простою вимірювання не спостерігалися. Зміни політики скидають віртуальну роботу й повторно перевіряють умови. Відновлення після півночі перевіряється раз на 30 секунд; календарна дата, а не фіксовані 24 години, враховує DST.

Кілька записів мають незалежні таймери. За однакових вибраних PV/load-сутностей зарезервована потужність віртуальних сусідів віднімається з бюджету; оновлення інших записів відбувається на наступній події/30-секундному tick. Якщо одна фізична СЕС представлена різними alias-сенсорами, спільний бюджет автоматично не визначається. Центральний арбітраж і пріоритети кондиціонерів ще не реалізовано.

## Діагностика

- Дія: «Запустив би», «Продовжив би», «Вимкнув би», «Очікував би».
- Окрема причина енергетичної стратегії; температурна причина збережена.
- Віртуальний стан, енергетичний дозвіл старту, мережа, ручна пауза та здоров’я енергетичних даних.
- SOC, нормалізовані потужності, залишок сонячного й прогнозного бюджетів, активні таймери.

Від’ємний бюджет означає дефіцит **після** оцінки AC та резервів. Дозвіл старту не означає, що є температурна потреба або завершені таймери. Стан «Вимкнув би» є переходом; наступна перевірка відображає очікування. Часові сенсори й power-сенсори доступні для стандартної картки HA.

## Перевірки та межі

Локальні тести перевіряють цикли, таймери, критичний SOC, зарядний пріоритет, дефіцит/відключення, обмежений імпорт, ручні зміни, відновлення, використання старих числових прогнозів та відхилення застарілих фактичних вимірювань. Окремий AST-тест блокує появу прямих сервісних команд у демо-коді. Повні HA-тести потребують локального HA test harness; не підміняються перевірками чистого ядра.

Це перша стратегія, а не модель компресора чи енергосистеми. Не симулюються фізична зміна SOC, температура приміщення, регулювання PV або змінне споживання компресора. Калібрування, Quiet/fan-комфорт, точна атрибуція команд і реальне керування ще не реалізовані.
