# Архітектура Solar Climate Manager

Поточна демо-стратегія 0.2.0 описана в [demo-strategy.md](demo-strategy.md). `strategy.py` — чисте ядро енергетичного рішення та віртуального циклу; `forecast.py` перевіряє покриття періодів; `manual.py` відстежує тільки керовані атрибути й календарну дату паузи; `settings.py` містить метадані політики для UI. Жоден із цих модулів не імпортує API управління пристроями. Store додатково зберігає віртуальний цикл, сигнатуру політики й дату ручної паузи. Наступні розділи описують базову архітектуру та план розвитку.

## Модулі

| Модуль | Відповідальність |
|---|---|
| `model.py` | Чистий термостат, перевірка чисел, перетворення температури, перевірка часових міток |
| `config_flow.py` | Вибір сутностей, валідація режимів, параметри, унікальність кондиціонера |
| `coordinator.py` | Знімок HA-станів, події, freshness tick, діагностичне рішення, Store |
| `entity.py` | Стабільні unique IDs і незалежний пристрій для запису |
| `sensor.py`, `binary_sensor.py` | Відображення результатів без команд |
| `switch.py` | Постійне увімкнення/вимкнення спостереження |
| `diagnostics.py` | Безпечний експорт параметрів і рішення |
| `__init__.py` | Setup, forwarding платформ, unload і завершення збереження |

Config entry data містить `climate_entity`, `temperature_entity`, `target_temperature`, `hysteresis`, `hvac_mode`, `max_data_age`, `enabled`. Options має пріоритет над data. Вибір кондиціонера є ідентичністю запису; зміни температурного датчика й параметрів відкидають старий latch. Observation-only — інваріант 0.1, а не вимикач, який може випадково дозволити керування.

Store має окремий ключ за entry ID і версію схеми 1. Зберігаються `demand` та сигнатура параметрів, потрібна для сумісності latch після restart. При недоступних даних latch скидається. Файловий I/O виконує HA Store асинхронно; unload очікує запис до повторного завантаження. Немає абсолютних таймерів, керуючих команд чи залежності від локального часу у 0.1.

## Додавання енергетики — 0.2

У 0.1.1 `power.py` додає незалежну валідацію W/kW і свіжості повідомлень. `POWER_SOURCES` містить mappings для фактичної PV-потужності та прогнозів зараз/+30/+60 хвилин. Optional джерела вибираються у Config/Options Flow; `None` в options від’єднує джерело з data. Чотири сенсори POWER/MEASUREMENT не впливають на термостат і не обчислюють надлишок. Обмеження свіжості прогнозу стосується часу повідомлення HA, а не часу отримання прогнозу від провайдера.

Додати чисті `energy.py` і `timers.py`, типізований знімок із валідністю кожного показника, окремий `forecast.py` для атрибутів Solcast. Знаки battery/grid та одиниці W/kW задаються конфігурацією. Заборонити старт за відсутності критичних даних; forecast не підміняє фактичні вимірювання. Показники навантаження мають явно описувати, чи включають кондиціонер, щоб не рахувати його двічі.

Температурна потреба існує незалежно від енергетичного дозволу. Рішення отримує стабільний reason code та параметри пояснення. Перевірка потенційного надлишку при curtailment використовує кілька джерел, консервативний запас і обмежений контрольований запуск із перевіркою імпорту/розряду після старту. Дефіцит і відсутність мережі мають незалежні часові мітки; аварійний SOC обходить мінімальний час роботи. Сам інвертор інтеграція ніколи не змінює.

Реальний `controller.py` додати лише разом із запобіжниками: asyncio lock на кондиціонер, послідовні команди, перевірка актуальності перед командою, ідемпотентність і журнал очікуваних підтверджень. Конфліктні власники того самого кондиціонера потребують явної конфігурації; без автоматичного переписування чужих змін.

## Ручний пріоритет і розклад — 0.3

`manual.py` відстежує лише керовані атрибути: HVAC mode, setpoint, fan, preset і окремі настроювані сутності Quiet. Зміни current_temperature/HVAC action не є ручною командою. Використовувати context, bounded command ledger, expected values та acknowledgement timeout; невизначені зміни трактувати консервативно як зовнішні. Не обіцяти достовірної ідентифікації фізичного пульта.

Зберігати режим automatic/manual-until-midnight/disabled, локальну дату manual pause, ownership і UTC-моменти старту/зупинки. При restart звіряти фактичний стан та не надсилати старт без нового повного рішення. Midnight визначати за timezone HA через наступну локальну календарну дату, а не `now + 24h`, щоб врахувати DST. У ручній паузі команди, зокрема аварійне вимкнення, не надсилаються; критична ситуація стає діагностикою.

`schedule.py`: інтервали з днями початку, overnight-продовженням на наступну дату; пріоритет forbidden > quiet > normal; для однотипних перетинів використовувати явний priority і стабільний порядок. Quiet/fan задавати лише за заявленими можливостями пристрою; не використовувати їх як точне обмеження потужності, Xtra fan не є boost-компресором.

## Калібрування — 0.4

`calibration.py` зберігає незалежні профілі heat/cool і довіру: середнє, підвищений квантиль, спостережений максимум. Спочатку використовувати консервативну ручну оцінку. Окремий AC power sensor має пріоритет; різниця загального навантаження потребує стабільного baseline, затримки стабілізації та фільтрації спотворень. Одночасні старти кількох кондиціонерів не використовувати для атрибуції різниці. Навчання не створює додаткових запусків поза комфортом, розкладом, енергетикою та ручним пріоритетом.
