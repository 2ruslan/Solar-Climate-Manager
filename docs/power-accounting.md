# Облік потужності учасника групи — 0.6.0

Індивідуальний датчик необов’язковий. Група може одночасно містити пристрої з датчиками та пристрої із заданою потужністю. Загальні енергетичні джерела групи залишаються потрібними. Автоматичне навчання споживання ще не реалізоване: це етап 11.

## Налаштування

1. Переведіть відповідний пристрій у **Лише спостереження** та дочекайтеся завершення команд і резервів.
2. Відкрийте **Налаштувати → Енергетика** запису, який уже входить до групи.
3. Виберіть **Облік потужності в групі**:
   - **За індивідуальним датчиком** (`meter`): датчик обов’язковий, W або kW; недоступне вимірювання не замінюється оцінкою.
   - **За заданою потужністю** (`estimated`): датчик не потрібний. Збережений датчик у груповому розрахунку ігнорується.
   - **Автоматично: датчик або задана потужність** (`legacy`): з налаштованим лічильником використовує його показники; без лічильника застосовує правила estimated. Задана потужність зберігається без додаткового процентного запасу; для явного запасу виберіть estimated.
4. Для estimated задайте електричну потужність (100–10000 W), запас (0–100%, типово 20%) та стабілізацію (30–1800 с, типово 120 с).
5. Перевірте прогноз у спостереженні, потім вмикайте керування по одному учаснику.

Приклад: 800 W і запас 20% дають планову потужність 960 W. Йдеться про електричне споживання, не теплову продуктивність. У meter/legacy оцінка використовується для резерву запуску без нового процентного запасу. Налаштування групового способу обліку не змінює незалежну стратегію після виходу з групи.

## Запуск і облік

До сервісного виклику стійко записується резерв. Одночасно група виконує лише один незавершений запуск. У estimated зняття резерву потребує всіх умов:

- сервіс завершився успішно; сам факт повернення сервісу недостатній;
- новий звіт climate підтвердив режим і ціль команди після її фактичного відправлення;
- кондиціонер досі має відомий увімкнений стан;
- після підтвердження минув час стабілізації;
- загальний лічильник надіслав актуальний звіт **після кінця** цього інтервалу; за активного мережевого ліміту потрібний також новий звіт імпорту;
- решта джерел і учасників доступні та узгоджені.

Саме очікування таймера без нового звіту нічого не підтверджує. Час перевіряється за HA last_reported; джерело, що не надсилає повторних показів при незмінному значенні, може затримувати запуск. Після ручного запуску estimated-учасника наступні запуски також чекають стабілізації та загальних звітів.

За `includes_all_members` загальний load уже містить споживання кондиціонерів. Після узгодження резерву оцінка повторно не додається; вона не віднімається від load для вигаданого вимірювання фонового навантаження. Загальний load може бути меншим за оцінку інверторного кондиціонера — це не помилка. До узгодження резерв залишається додатковим консервативним запасом.

За `excludes_all_members` до load додається потужність учасників: виміряна для meter/legacy або оцінка із запасом для працюючого estimated. Поки є незавершений estimated-резерв, його величина вже врахована резервом, тому для цього учасника додається лише початкове споживання. Після узгодження його замінює поточна оцінка — подвійного додавання немає. Вимкнений estimated-пристрій має оцінку 0 W; за потреби обліку standby використовуйте індивідуальний датчик або загальний лічильник, який включає пристрої.

За мережевого ліміту використовуються фактичний загальний імпорт і незавершений резерв. Поточна оцінка не додається повторно до виміряного імпорту. Часткове покриття кондиціонерів загальним лічильником не підтримується.

Оцінка є припущенням для планування. Свіжий загальний звіт не доводить точну потужність конкретного кондиціонера й не гарантує, що компресор уже досяг максимального споживання. Вибирайте достатню оцінку та стабілізацію відповідно до пристрою; автоматичне визначення його профілю тут не виконується.

## Помилки та відновлення

Timeout, скасування, помилка сервісу, reload або restart із незавершеним стартом зберігають невизначений резерв. У estimated звичайний звіт про роботу не знімає його. У режимі control GroupManager відправляє захисний off; звільнення потребує нового off після фактичної відправки та актуальних загальних вимірювань після стабілізації від часу stop. Підтверджений off очікує вимірювань без повторних команд, які перезапускали б таймер. У observation/disabled команди не надсилаються.

Старі записи без нового параметра залишаються legacy у збережених налаштуваннях, режими та групи не змінюються. Без налаштованого лічильника фактичний спосіб обліку стає estimated автоматично. Старий резерв зберігається до захисної зупинки, нового звіту off та свіжих загальних показників після стабілізації; після цього дозволений новий запуск. Налаштований, але недоступний лічильник не замінюється оцінкою. Змінювати спосіб, потужність, запас або стабілізацію за активного control чи незавершеного резерву заборонено. Не видаляйте Store для обходу блокування.

## Прогноз при запуску

Група враховує мінімум актуальних прогнозів сонячної потужності на зараз, +30 і +60 хвилин. Очікуване падіння генерації зменшує бюджет нових запусків: у автономному режимі — сонячний запас, за наявної мережі та ліміту імпорту — запас цього ліміту. Очікуване зростання не замінює поточну доступну потужність. Без повного валідного прогнозу рішення спирається на поточні вимірювання; за необмеженої мережі прогноз не блокує запуск. Прогноз не підтверджує виконання команд і не спричиняє зупинку працюючого пристрою сам по собі.

Історія містить збережений `power_accounting` та фактичний `effective_power_accounting`, щоб автоматичний вибір оцінки був видимий.

Config entries v2, Store пристрою v1 та внутрішня групова схема v2 не змінюються. Для відкату використовуйте узгоджену резервну копію, як описано в [інструкції перевірки](group-rollout.md).

## Діагностика

Стан підтвердження групової команди показує **Очікування стабілізації загального навантаження** (`awaiting_stabilization`). Атрибути сутності **Рішення групи** містять `power_accounting`, `planned_start_power_w`, `power_margin_percent` та `power_settle_seconds`. Наявні IDs сутностей збережені. Оцінка не видається за показ індивідуального датчика; старий sensor виміряної потужності, якщо датчик заданий, може показувати його фактичні дані, але в estimated груповий розрахунок їх не використовує.
