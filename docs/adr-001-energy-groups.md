# ADR 001: енергетична група та стабільна ідентичність

Статус: прийнято, етап 5. Дата: 2026-10-15.

## Рішення та межі етапу

Один config entry залишається одним кондиціонером. Групи зберігаються в окремому HA Store `solar_climate_manager.groups` версії 1. Усередині — `schema_version: 1`, списки `groups`, `memberships`, `unresolved`. Це єдине джерело конфігурації груп і членства; group_id не дублюється в data/options пристроїв.

Реєстр на цьому етапі є підготовленою конфігурацією. Він не підключений до чинного командного шляху: не створює стартів, не змінює режимів і не координує незалежні записи. Не можна трактувати заповнений реєстр як увімкнене групове керування. Етап 6 додає спостереження за розподілом; етап 7 підключає єдиний шлях авторизації групових команд; етап 8 додає UI. До цього створення/приєднання доступне тільки внутрішньому API й тестам, без публічного сервісу.

## Ідентичність і сумісність

Config flow переходить з версії 1 на 2. Міграція через `async_migrate_entry` додає `data.device_id`, використовуючи наявний незмінний `entry_id`; нові записи отримують UUID. Значення не залежить від climate entity_id, назви чи датчиків. `entry_id`, `unique_id` та entity unique IDs зберігаються. Майбутня підтримка reconfigure має зберігати device_id.

`device_id` є метаданими й вилучається з нормалізованих налаштувань політики. Тому міграція не змінює сигнатури температурної потреби або політики. Options, режими, ручне блокування та Store пристрою версії 1 залишаються без змін. Старі одиночні записи й два незалежні записи не отримують членства. Міграція не активує control. Непідтримувана майбутня версія конфігурації відхиляється.

Зміна major-версії означає: для повернення до коду до етапу 5 слід відновити резервну копію config entries, а не розраховувати на читання v2 старим кодом. Сховище стану самого пристрою не потребує зміни формату.

API міграції перевірено за [документацією Config Flow](https://developers.home-assistant.io/docs/core/integration/config_flow/) та [правилом async_update_entry](https://developers.home-assistant.io/blog/2024/02/12/async_update_entry/), а реалізацію — тестами на HA 2026.10.1.

## Власники параметрів

| Група | Пристрій |
|---|---|
| PV, загальне навантаження, SOC, батарея, мережа, ліміт імпорту, прогноз | climate, кімнатна температура, індивідуальний лічильник, розклад |
| Пороги minimum/restart SOC, максимум розряду, затримки енергетичних рішень і втрати мережі, актуальність джерел | Температура, гістерезис, HVAC mode, межі цілі, режим автоматизації, ручне блокування |
| Знаки мережі/батареї, значення binary_sensor мережі, склад загального навантаження | Оцінка потужності, мінімальний час роботи/простою, фактичні таймери |
| Єдина спільна політика без локальних перевизначень учасниками | Пріоритет належить запису Membership |

`GroupSources`, `GroupPolicy` і `MemberPolicy` задають ці межі. Поточний незалежний шлях продовжує використовувати попередні налаштування. При майбутньому приєднанні локальні енергетичні налаштування зберігатимуться для виходу з групи, але групові рішення використовуватимуть виключно GroupPolicy.

У груповому snapshot SOC має одну семантику: низький поріг блокує, відновлення — за restart_soc. Немає усереднення SOC між учасниками. Імпорт мережі нормалізується як позитивний; позитивна батарея означає розряд. Спільний ліміт імпорту порівнюється з одним загальним лічильником мережі й враховується один раз. Налаштований, але відсутній ліміт/лічильник не перетворюється на нуль або безлімітний дозвіл.

## Контракт обліку навантаження

`load_scope` має два явні значення:

- `includes_all_members`: загальний лічильник уже містить усі кондиціонери групи. Для базового навантаження віднімається сума індивідуального споживання рівно один раз; поточне навантаження учасників додається рівно один раз при розрахунку доступної потужності.
- `excludes_all_members`: лічильник не містить жодного учасника; до нього додається сума потужностей усіх учасників.

Змішане покриття лічильником не підтримується: перед приєднанням потрібен окремий агрегований сенсор із визначеним покриттям. Старий `load_includes_ac` не переноситься автоматично на групу, бо не описує кілька пристроїв.

Якщо загальний load містить заряд батареї, він вилучається з базового домашнього навантаження один раз за `load_includes_battery_charging`. Негативний результат або неузгоджені вимірювання означають неповний бюджет, а не додаткову вільну потужність. Лічильник мережі для перевірки ліміту вже містить реальне споживання: до нього додається лише прогнозований приріст/незавершений резерв, а не все поточне споживання кондиціонерів повторно.

Потужність учасника враховується незалежно від його mode, demand та авторства команди: ручний запуск також витрачає бюджет. Валідний індивідуальний лічильник має пріоритет, включно зі споживанням standby при off. За відсутності налаштованого індивідуального лічильника використовується estimated_ac_power для відомого running; така оцінка позначається як оцінка і сама по собі не підтверджує облік резерву. Відсутній налаштований лічильник або невідомий фізичний стан — неповні дані. Оцінка не може сама звільнити незавершений резерв або довести вільну потужність за суперечливих даних. Конкретний розрахунок/узгодження реалізується в allocator на етапі 6.

## Життєвий цикл реєстру

`GroupRepository` створюється один раз на HA instance; одна asyncio.Lock серіалізує load і зміни. Читання через `async_load`; зміна через `async_update`, що застосовує чисте перетворення GroupRegistry й спочатку записує результат у Store. Лише успішне збереження публікує новий незмінний реєстр. Помилка запису залишає попередній стан. Незалежні записи не залежать від завантаження групового сховища.

`create` генерує UUID групи; перейменування/зміна джерел зберігає group_id. `join` додає Membership явно й відхиляє повторне членство навіть у тій самій групі. `leave` знімає членство; перенесення — явні leave/join. Групу можна видалити лише без учасників і резервів. При майбутньому видаленні config entry потрібне явне від’єднання: відсутній учасник залишається заблокованим членством, а не тихо вилучається з бюджету.

Формат v1 читається без втрат; відсутній Store означає порожній реєстр. Невідома schema_version, пошкоджені записи чи подвійне членство відхиляються. Невідомі дані не перезаписуються порожньою структурою. Посилання на відсутню групу зберігаються для відновлення й мають стан missing_group.

## Неповні дані, reload і резерви

`readiness(group_id, loaded_devices)` розрізняє missing_group, incomplete_sources, no_members, members_unavailable, unresolved_reservation і configured. configured означає лише готовність конфігурації: це **не дозвіл старту**. Актуальність snapshot, бюджет і наявність мережі перевірятиме allocator. Усі інші стани забороняють нові групові старти; чинні незалежні записи на етапі 5 не перемикаються автоматично в груповий режим.

При reload учасник тимчасово відсутній у loaded_devices, членство зберігається. Неврегульовані резерви зберігаються як device_id/group_id/watts у Store й не зникають при зміні конфігурації, reload або відсутності групи. leave/перенесення/видалення блокуються за такого резерву. Резерв не звільняється через повернення сервісу, timeout, unload або скасування. Етап 6 додасть його життєвий цикл; етап 7 — реальні резерви перед командами. Наразі реальні резерви не створюються.

Після змін складу або джерел майбутній runtime групи має відкинути старий розрахунок і зібрати повний snapshot перед новими стартами, зберігши невизначені резерви. Втрата повноти бюджету не є доказом зупинки пристрою. Захисні зупинки та їх пріоритет підключаються окремо на етапі 7.
