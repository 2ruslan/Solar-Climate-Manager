# Solar Climate Manager

<img src="custom_components/solar_climate_manager/brand/icon.png" alt="Solar Climate Manager — сонце та вентилятор" width="96" height="96">

Інтеграція Home Assistant для автоматичного керування кондиціонером за кімнатною температурою, зарядом батареї, сонячним балансом і доступністю мережі. Підтримує обігрів та охолодження; кожен кондиціонер має окремий запис і налаштування. У версії **0.8.1** кілька записів можна явно об’єднати в енергетичну групу зі спільним бюджетом і пріоритетами.

[![Відкрити Solar Climate Manager у HACS](https://my.home-assistant.io/badges/hacs_repository.svg)](https://my.home-assistant.io/redirect/hacs_repository/?owner=2ruslan&repository=Solar-Climate-Manager&category=integration)

## Встановлення та налаштування

На головній сторінці також показано кількість працюючих і недоступних пристроїв. Історія доступна за кнопкою «Історія та діагностика» у картці кондиціонера.

На головній сторінці Solar Climate Manager налаштування доступні без додаткових вікон у згортаних блоках. У картці енергетичної групи розташовані спільні **Мережа**, **Батарея**, **Сонячна генерація** та **Споживання**. У картці кондиціонера — **Клімат і розклад**, власне **Споживання**, прив’язки пристрою та назва/пріоритет у групі. Для незалежного кондиціонера всі п’ять тематичних блоків розташовані в його картці. Кожен блок має **Зберегти** та **Скасувати**; вибору «Дія» на головній сторінці немає. Фонове оновлення не перезаписує відкриті форми; застарілі зміни відхиляються. Створення/видалення груп, зміна членства та скидання навчання залишаються окремими операціями з підтвердженням.

1. Додайте `https://github.com/2ruslan/Solar-Climate-Manager` у HACS як користувацький репозиторій типу Integration, завантажте інтеграцію та перезапустіть HA. Для ручного встановлення скопіюйте `custom_components/solar_climate_manager` у `/config/custom_components/solar_climate_manager`.
2. Через **Налаштування → Пристрої та служби → Додати інтеграцію** виберіть Solar Climate Manager. Задайте кондиціонер, датчик кімнатної температури, обігрів або охолодження, ціль і температурний гістерезис. Ціль задається у °C; покази та команди у °F перетворюються автоматично.
3. На сторінці інтеграції натисніть **шестерню біля потрібного запису кондиціонера**. Одразу відкриється одна форма з групами **Клімат і розклад**, **Мережа**, **Батарея**, **Сонячна генерація**, **Споживання**. Групи можна згортати; датчики та їхні параметри розміщені поруч. Для учасника енергетичної групи тут доступні власний клімат і споживання. Спільні параметри доступні через дію **Перейти до керування енергетичною групою**. Цей перехід не зберігає зміни форми: спочатку збережіть їх окремо. Шестерня самої сутності змінює її назву й відображення, а не параметри контролера.
4. У **Батареї** задайте датчики SOC і потужності, у **Мережі** — наявність мережі та імпорт/експорт. Для автономної роботи потрібні також **Сонячна генерація** і **Споживання**. Перевірте знак потужності батареї та мережі, чи включає споживання кондиціонер і заряджання батареї. Прогноз СЕС не використовується: рішення спираються на поточні вимірювання.
5. У **Кліматі і розкладі** задайте температуру, гістерезис і, за потреби, розклад. Без вибраного розкладу робота дозволена весь час. У **Споживанні** задайте оцінку потужності кондиціонера, у **Батареї** — два пороги заряду, у **Мережі** — затримку захисної зупинки за відсутності мережі. Дія **Зберегти налаштування** застосовує всі зміни форми разом.
6. На сторінці пристрою виберіть **Режим роботи**. Після встановлення діє спостереження; автоматичні команди починаються після вибору повного управління та виконання умов стратегії.

Для другого кондиціонера додайте окремий запис. Повторне додавання того самого `climate` блокується. Для розподілу спільного бюджету явно об’єднайте записи в енергетичну групу; незалежні записи не координують його між собою.

У групі старий режим `legacy` без налаштованого датчика потужності автоматично використовує задану оцінку споживання. Завислий резерв після оновлення знімається через підтверджену захисну зупинку та свіжі загальні показники після стабілізації (типово 120 с). Після цього запуск знову дозволений за достатнього поточного бюджету. Наявний, але недоступний датчик не підміняється оцінкою. [Облік потужності та відновлення](docs/power-accounting.md).

## Сторінка керування

У бічному меню адміністратора доступна **Solar Climate Manager**: групи та їхній бюджет, пристрої, режими й налаштування в одному місці. Тут можна створювати групи, приєднувати кондиціонери та задавати потужність без індивідуальних датчиків. Після оновлення перезапустіть HA. [Покрокова інструкція](docs/manager-panel.md).

Навчання потужності можна явно ввімкнути для групового обліку за оцінкою. Воно використовує повторні окремі запуски й загальний лічильник, зберігаючи задану потужність як нижню межу. [Правила та обмеження навчання](docs/power-learning.md).

## Чотири статуси роботи

| Статус | Поведінка |
|---|---|
| Все вимкнено | Температурна потреба вимкнена, автоматичні команди не надсилаються. Діагностика джерел та енергетичного дозволу продовжує оновлюватися. |
| Лише спостереження | Показує дані та рішення стратегії без команд кондиціонеру. Типовий статус після встановлення. |
| Повне управління | Запускає кондиціонер у вибраному режимі з розрахованою ціллю та вимикає його за рішенням стратегії. |
| Тимчасове блокування | Припиняє автоматичні команди до місцевої півночі HA, після чого повертає попередній статус. Можна встановити вручну або зняти, вибравши інший статус. |

Вибір вимкнення, спостереження чи тимчасового блокування залишає кондиціонер у поточному фізичному стані. Статус зберігається після перезапуску та зміни налаштувань. Датчик «Кондиціонер увімкнено» показує стан реального `climate`; рішення «Запуск» у спостереженні є рекомендацією.

Зовнішні зміни режиму, цілі, вентилятора або інших керованих атрибутів автоматично встановлюють тимчасове блокування. Попередній статус та дата зберігаються; повторні ручні зміни під час блокування не змінюють статус повернення. Повернення відбувається на першій перевірці після місцевої півночі (таймер кожні 30 секунд). Вибір іншого статусу знімає блокування одразу та скасовує повернення опівночі.

Власні команди розпізнаються за контекстом HA або точним збігом змінених полів з очікуваною відповіддю протягом 30 секунд. Явні користувацькі команди й неочікувані зміни вважаються ручними. Зміна виміряної температури кондиціонера сама по собі не встановлює блокування.

## Кілька кондиціонерів: енергетична група

Наявні записи залишаються незалежними після оновлення. Щоб розподіляти один бюджет між кондиціонерами, переведіть їх у **Спостереження** та відкрийте **Налаштувати → Енергетична група**. Перший запис: **Створити групу** → назва/пріоритет → джерела → правила. Інші записи: **Приєднатися до групи**. Група не перемикає режими автоматично.

Спільними стають PV, загальне навантаження, батарея, мережа та енергетична політика. Температура, розклад, оцінка споживання й індивідуальний лічильник залишаються власними для кожного кондиціонера. Більший пріоритет означає раніший старт; рівність розв’язує стабільний device_id. Не створюйте різні групи для одного фізичного енергетичного бюджету.

Перед стартом записується резерв потужності. Індивідуальні лічильники необов’язкові: у **Налаштувати → Енергетика** учасника виберіть **За заданою потужністю**, задайте електричну потужність, запас (типово 20%) і стабілізацію (типово 120 с). Наступний старт чекає успішної команди, підтвердження climate та свіжих загальних вимірювань після стабілізації. Timeout або restart не звільняють резерв. Наявні записи залишаються в режимі **Попередня поведінка (0.5.0)** до явного вибору нового обліку. Підтримуються змішані групи з датчиками й оцінками. [Докладні правила обліку](docs/power-accounting.md). Повільний сервіс одного пристрою не блокує захисну зупинку іншого.

Нові діагностичні сутності: група, доступна потужність, навантаження, реальний резерв, рішення, причина та підтвердження команди. У observation рішення позначене як **Прогноз**. Групові потужності однакові у всіх учасників — не підсумовуйте їх. За необмеженої мережі числова доступна потужність не показується. Старі одиночні сенсори залишені для сумісності й описують локальну стратегію; для групового рішення використовуйте нові сутності.

**⋮ → Переналаштувати** змінює кондиціонер, датчик кімнати та heat/cool зі збереженням ID, групи й режиму. UI відхиляє дубль кондиціонера та небезпечну зміну прив’язок під час керування/незавершених команд. Зміна джерел/правил групи потребує призупинення control її учасників; після перевірки ви самі повертаєте потрібні пристрої в control.

[Перевірка на сервері та відновлення резервної копії](docs/group-rollout.md) · [Картка для двох кондиціонерів](docs/lovelace-group-card.yaml) · [Правила групового бюджету](docs/group-allocation.md).

Наведені нижче розділи сонячного балансу й таймерів описують незалежний пристрій. Для групи діє поточний спільний бюджет із підтвердженням виконання команд, описаний у правилах групи.

## Два пороги заряду батареї

У **Налаштувати → Енергетика**:

| Параметр | Типове значення | Призначення |
|---|---|---|
| Заряд для зупинки | 85% | Без мережі заряд нижче цього порога негайно зупиняє автоматичну роботу. На самій межі працюючий кондиціонер може продовжувати роботу. |
| Заряд для відновлення роботи | 90% | Без мережі запуск дозволяється від цього рівня заряду, за виконання решти умов. Після блокування нижній поріг сам по собі вже не дозволяє запуск. |

Верхній поріг має бути вищим за нижній. Наприклад: після падіння нижче 85% автоматизація чекає 90%; підвищення до 85–89% не запускає кондиціонер. Після запуску зниження до 89% не зупиняє його — зупинка за зарядом настане нижче 85%. Це запобігає циклам біля однієї межі. Блокування за зарядом зберігається після перезапуску й редагування налаштувань та не скасовується перемиканням статусу автоматизації.

Під час оновлення старий мінімальний SOC стає порогом зупинки. Поріг відновлення додається автоматично: на 5 відсоткових пунктів вище, максимум 100%. Для старого порога 100% утворюється пара 99% / 100%, щоб залишити різні межі. Наявні два пороги зберігаються.

За наявності мережі та налаштованого додатного ліміту імпорту кондиціонер може запускатися й працювати навіть нижче обох порогів SOC та під час розряду батареї, якщо вистачає бюджету імпорту. Це діє для окремого кондиціонера й групи; відсутній або некоректний ліміт чи показник імпорту блокує дозвіл. Без налаштованого ліміту або за ліміту 0 розряд батареї та низький SOC не блокують роботу від мережі. Блокування SOC зберігається для захисту після зникнення мережі. Окремого таймера зупинки за розрядом немає.

## Сонячний баланс і таймери

За доступної мережі СЕС не потрібна. Без мережі запуск потребує заряду не нижче верхнього порога та невід’ємного поточного сонячного балансу. Баланс враховує споживання будинку та оцінку потужності кондиціонера. Вибрані прапорці визначають, чи потрібно відняти вже включене споживання кондиціонера та заряджання батареї.

Сонячний дефіцит враховується одразу, без окремого таймера дефіциту. Для незалежного пристрою захисна зупинка за дефіцитом залежить від таймера відсутності мережі (налаштовується, типово 10 хвилин); у групі — від завершення мінімального часу роботи або таймера відсутності мережі. Мінімальна робота та пауза між циклами — по 10 хвилин. Захист заряду, даних, імпортного ліміту та розкладу може зупиняти раніше. Відновлення заряду не скасовує мінімальну паузу та перевірку сонячного балансу.

Енергетичний дозвіл оцінюється незалежно від статусу автоматизації, розкладу й температурної потреби. Увімкнений дозвіл ще не означає запуск: причина рішення стратегії показує, що саме очікується.

## Температура і команди кондиціонеру

Для обігріву потреба виникає нижче **ціль − гістерезис**, а зникає вище **ціль + гістерезис**; для охолодження умови протилежні. Усередині діапазону й на його межах зберігається попереднє рішення.

Ціль кондиціонера компенсує різницю датчиків:

**Ціль кондиціонера = кімнатна ціль + температура кондиціонера − кімнатна температура.**

Наприклад, ціль кімнати 22 °C, у кімнаті 20 °C, кондиціонер бачить 25 °C: команда становить 27 °C. Результат обмежується налаштованими межами команд та допустимим діапазоном пристрою й округлюється до його кроку без виходу за межі. Формула однакова для обігріву й охолодження; заводська компенсація конкретної моделі може впливати на результат.

У **Налаштувати → Клімат і розклад** задаються **Мінімальна температура команди кондиціонеру** (типово 15 °C) та **Максимальна температура команди кондиціонеру** (типово 27 °C). Вони доступні також під час додавання інтеграції. Це межі команд кондиціонеру, окремі від бажаної кімнатної температури. Наприклад, розраховані 29 °C обмежуються до 27 °C; якщо пристрій підтримує мінімум 16 °C, команда не опуститься до налаштованих 15 °C. Межі можна змінити; діапазон має містити хоча б одну температуру, яку підтримує пристрій. Після оновлення наявні записи отримують типові межі 15–27 °C.

Під час роботи нова компенсована ціль надсилається лише коли залишковий запас **менший за 1,1 °C**: для обігріву це встановлена ціль мінус температура кондиціонера, для охолодження — температура кондиціонера мінус встановлена ціль. Наприклад, за цілі 26 °C та показу 24 °C ціль залишається; за показу 25 °C компенсація перераховується. На межі 1,1 °C ціль залишається. Якщо після обмеження й округлення нова ціль збігається з установленою, команда не повторюється. Початковий запуск, зміна режиму та виправлення цілі поза дозволеними межами виконуються незалежно від цього запасу.

Температура кондиціонера читається з `current_temperature`. Якщо вона відсутня або некоректна, запуск блокується, а у повному управлінні працюючий кондиціонер зупиняється. Діагностика показує обидві температури, різницю, розраховану та встановлену цілі. Додатково коригування цілі обмежене одним разом на хвилину; захисна зупинка цього інтервалу не чекає.

Кімнатний датчик може повідомляти лише зміни: останній коректний показ не має обмеження віку. `unknown`, `unavailable`, відсутнє джерело або некоректне значення блокують роботу. Фактичні енергетичні покази перевіряються через `last_reported`: максимум 15 хвилин; наявність мережі та налаштування імпортного ліміту не мають обмеження віку. Недоступні значення не замінюються нулями.

Помилка сервісу не вважається успішним запуском. Очікування команди обмежено 10 секундами, повтор однакової команди — інтервалом 30 секунд. Після завершення команди рішення перевіряється знову. Помилка та причини блокування доступні в діагностичних сутностях. Інтеграція не керує вентиляторами, Quiet-режимом чи режимами інвертора.

## Ліміт імпорту з інвертора

У **Налаштувати → Мережа** необов’язково виберіть `number` із лімітом імпорту, наприклад `number.inverter_grid_peak_shaving`. Одиниці W або kW читаються з атрибутів. **0 або невибране джерело означають відсутність ліміту.** Додатний ліміт потребує датчика фактичної потужності імпорту/експорту мережі.

Перед запуском перевіряється **фактичний імпорт + оцінка споживання кондиціонера ≤ ліміт**. Фактичний імпорт уже включає заряджання батареї; воно не віднімається заради запуску. Експорт має від’ємний знак і збільшує запас. Під час роботи кондиціонер уже включений у імпорт, тому його оцінка вдруге не додається.

Перевищення ліміту зупиняє автоматичну роботу без очікування мінімального часу циклу. Недоступний вибраний ліміт або вимір імпорту блокує роботу від мережі; без мережі діють правила сонячного балансу й заряду. Інтеграція читає ліміт, але не змінює його: апаратне обмеження виконує інвертор.

## Оновлення, картка та перевірка

Після оновлення файлів перезапустіть HA й оновіть сторінку браузера. Видаляти та повторно додавати запис не потрібно. Джерела, комфорт, статус та налаштований поріг зупинки зберігаються. Старі записи з `enabled` переходять у спостереження або вимкнення; стара окрема ручна пауза переходить у тимчасове блокування.

[Готова картка YAML](docs/lovelace-card.yaml) і [підстановка сутностей](docs/dashboard-card.md) містять статус, причини рішень, обидва пороги заряду, енергетичний баланс і графіки за 12 годин. Картка використовує стандартні компоненти HA; оновлений YAML потрібно застосувати окремо. Докладні правила: [стратегія](docs/strategy.md), [архітектура](docs/architecture.md).

Інструкція для розробки: [середовище, локальні перевірки та CI](docs/development.md).

Базова ціль HA-тестів: Home Assistant 2026.10.1, Python 3.14.2, Linux. Версії залежностей зафіксовані в `requirements/ha.txt`; unit-тести запускаються окремим процесом і також перевіряються на Python 3.11.

```sh
python -m pip install -r requirements/ha.txt
python -m pip check
python -m ruff check .
python -m mypy
python -m unittest discover -s tests/unit -v
python -m pytest -q tests/ha
```

Unit-тести перевіряють ядро й адаптер із моделями API; HA-тести — справжній життєвий цикл інтеграції. Роботу з фізичним кондиціонером перевіряйте у своїй інсталяції HA.
