# Solar Climate Manager — 0.2.5 (демо)

[![Відкрити Solar Climate Manager у HACS](https://my.home-assistant.io/badges/hacs_repository.svg)](https://my.home-assistant.io/redirect/hacs_repository/?owner=2ruslan&repository=Solar-Climate-Manager&category=integration)

Власна інтеграція Home Assistant для майбутнього керування кондиціонерами з урахуванням сонячної енергії. **Поточна версія працює виключно в демо: реальне керування увімкнути неможливо.**

**Версія 0.2.0 також працює виключно в демо.** Додано повні налаштування першої енергетичної стратегії та віртуальні цикли з SOC, навантаженням, мережею, прогнозом, таймерами, розкладом дозволу й ручною паузою. Команди кондиціонеру та інвертору не надсилаються. [Налаштування, правила й обмеження демо](docs/demo-strategy.md).

## Установлення через HACS

1. HACS має бути встановлений і налаштований у вашому Home Assistant.
2. Натисніть кнопку вище. Якщо My Home Assistant попросить адресу вашої інсталяції, вкажіть її.
3. У HACS підтвердьте додавання репозиторію та натисніть **Download / Завантажити**. Кнопка відкриває репозиторій; установлення потребує підтвердження в HACS.
4. Перезапустіть Home Assistant і додайте **Solar Climate Manager** через **Налаштування → Пристрої та служби → Додати інтеграцію**.

Якщо посилання не відкривається, у HACS відкрийте **Custom repositories / Користувацькі репозиторії**, додайте `https://github.com/2ruslan/Solar-Climate-Manager` із типом **Integration**, а потім завантажте інтеграцію.

## Установлення та перевірка

1. Скопіюйте каталог `custom_components/solar_climate_manager` у `/config/custom_components/solar_climate_manager` вашого Home Assistant, не змінюючи системних файлів.
2. Перезапустіть Home Assistant. Відкрийте **Налаштування → Пристрої та служби → Додати інтеграцію → Solar Climate Manager**.
3. Виберіть наявний кондиціонер і датчик температури кімнати. Датчик має оголошувати `device_class: temperature` та одиниці °C або °F. Назви реальних сутностей не зашиті в коді.
4. Задайте режим heat/cool, цільову температуру, гістерезис та максимальний вік температурних даних. Ціль і гістерезис у формі задаються у °C; покази °F перетворюються.
5. На сторінці пристрою перевірте температуру, потребу за температурою, причину рішення, стан даних і режим автоматизації. «Реальне керування дозволено» завжди вимкнено у 0.1.
6. Для target=23 і hysteresis=1 в обігріві потреба вмикається нижче 22 °C, вимикається вище 24 °C та зберігається між порогами, включно з межами. Для охолодження правила протилежні.
7. Змініть параметри через **Налаштувати**. Вимкніть перемикач «Спостереження», щоб припинити розрахунок потреби; це налаштування зберігається після перезапуску. Кондиціонер при цьому не вимикається.
8. Перевірте поведінку для `unavailable` і застарілої температури: потреба скидається, стан даних показує проблему. Повторний запуск HA в зоні гістерезису має зберігати попередню потребу, якщо джерело й параметри не змінилися.

Для другого кондиціонера створіть ще один запис інтеграції. Повторний запис для того самого `climate` блокується. Заміна кондиціонера виконується видаленням і створенням запису; датчик температури можна змінити в Options Flow.

## Що реалізовано

- Config Flow та Options Flow, незалежний запис для кожного кондиціонера.
- Чистий термостат з гістерезисом; відокремлена температурна потреба та дозвіл керування.
- Діагностичні `sensor`, `binary_sensor`, конфігураційний `switch`, експорт діагностики без ідентифікаторів вибраних сутностей.
- Англійська й українська локалізації.
- Асинхронне зберігання стану гістерезису через HA Store; налаштування зберігаються у config entry.
- Обробка подій стану та перевірка старіння кожні 30 секунд. Записи стану й журнал створюються лише за зміни результату; причини журналюються на рівні debug.

## Потужність СЕС і прогноз — 0.1.1

Після оновлення через HACS перезапустіть HA й відкрийте **Налаштувати** в інтеграції. Додано чотири необов’язкові джерела, без прив’язки до виробника:

| Поле | Джерело |
|---|---|
| Фактична потужність СЕС | Сумарна PV-потужність інвертора у W або kW |
| Прогноз потужності зараз | Solcast `Forecast Power Now` або сумісне джерело |
| Прогноз через 30 хвилин | Solcast `Forecast Power in 30 Minutes` або сумісне джерело |
| Прогноз через 1 годину | Solcast `Forecast Power in 1 Hour` або сумісне джерело |

Прогнози стосуються майбутніх моментів, а не середнього за інтервал. Датчики енергії Wh/kWh, зокрема `Forecast Next Hour`, не підходять. Якщо джерело не надає потрібний показник, залиште поле порожнім. Очищення поля від’єднує джерело, зокрема обране при первинному налаштуванні.

Чотири нові сенсори показують W. Максимальний вік фактичних вимірювань налаштовується: типово 900 секунд для PV. Прогнозні сенсори використовуються незалежно від віку повідомлення. Відсутність, некоректні числа та від’ємна потужність роблять відповідний сенсор недоступним; для фактичних вимірювань також перевіряється актуальність. Нуль залишається валідним показом. Температурна діагностика незалежна.

Актуальність фактичних вимірювань визначається за HA `last_reported`. Для прогнозу використовуються останні доступні коректні значення, без обмеження віку; окремого датчика часу оновлення або деталізації немає. Прогноз не є вимірюванням, фактична PV-потужність може бути обмежена інвертором; жоден показник окремо не доводить наявність надлишку. Реальне керування залишається заблокованим.

## Локальні тести

Без залежностей Home Assistant (Python ≥3.12):

```sh
python -m unittest discover -s tests/unit -v
python -m compileall -q custom_components tests
```

Для перевірки в реальному тестовому середовищі HA використовуйте Linux і версію Python, потрібну поточному Home Assistant:

```sh
python -m pip install ruff pytest-homeassistant-custom-component
ruff check .
pytest -q tests/ha
```

Усі тести запускаються локально наведеними командами. Інтеграційні тести перевіряють flows, дублікати, setup, відсутність сервісних викликів, недоступні й застарілі дані, reload і збереження вимкненого режиму. Не вважайте HA-тести виконаними, якщо доступне лише тестування ядра.

## Обмеження та публікація

Енергетична стратегія, таймери, ручна пауза та розклад дозволу вже доступні в демо 0.2.0. Реальне керування, Quiet/fan-комфорт, калібрування, центральний арбітраж кількох кондиціонерів і точна атрибуція джерела команд ще не реалізовані. Ручні зміни реального кондиціонера не перезаписуються.

Актуальність температури визначається через HA `last_reported`, що дозволяє незмінному, але повторно надісланому показу залишатися актуальним. Це час повідомлення в HA, а не гарантія часу фізичного вимірювання. Якщо upstream повторно публікує старі значення, потрібен окремий адаптер часових міток. Недоступний або несумісний кондиціонер також блокує температурне рішення; stale-перевірка стосується датчика температури.

HA API опрацьовано за актуальною офіційною документацією; перевірку на живій інсталяції необхідно виконати перед використанням. Мінімальна сумісна версія HA ще не сертифікована.

Проєкт опубліковано на GitHub для встановлення як користувацький репозиторій HACS. HACS/hassfest validation ще не виконано; до стандартного каталогу HACS проєкт не додано. Перед поданням до каталогу налаштуйте issue tracker, GitHub codeowner, ліцензію, metadata репозиторію та за потреби брендинг.

Архітектура й план наступних версій: [docs/architecture.md](docs/architecture.md).

Офіційні вимоги: [Config Flow](https://developers.home-assistant.io/docs/core/integration/config_flow/), [Options Flow](https://developers.home-assistant.io/docs/core/integration/options_flow/), [runtime_data](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/runtime-data/), [manifest](https://developers.home-assistant.io/docs/creating_integration_manifest/), [HACS](https://www.hacs.dev/docs/publish/integration/).

## Спрощені налаштування — 0.2.4

«Налаштувати» відкриває меню: **Джерела даних → Комфорт → Енергетика → Розширені** (незалежні розділи, не послідовні кроки). Редагування одного розділу зберігає інші, включно з вимкненим спостереженням. Ліміти імпорту й бюджету заряджання показуються наступним кроком енергетики лише для ввімкнених функцій; вимкнення функції не стирає збережений ліміт.

Прогноз і ручний пріоритет тепер постійні правила. Пробні старти за прогнозом видалено: запуск потребує фактичного надлишку або явно дозволеного обмеженого імпорту. Перемикач спостереження залишається на пристрої/картці, його дубль у формі прибрано. Під час нового додавання вибираються лише climate, температура та комфорт; енергетичні джерела вибираються через «Налаштувати» після додавання. До їх налаштування демо-старт заблокований.

## Спрощення 0.2.5

- Один мінімальний SOC; нижче нього негайна демо-зупинка.
- Немає критичного/бажаного SOC, запасів у ватах чи окремого зарядного сенсора.
- Для старту оцінюється середній баланс за 10 хвилин. Короткий пік споживання не скидає вікно й не зупиняє цикл; тривалий дефіцит — блокує старт або зупиняє роботу.
- У «Розширених» лише відсутність мережі у хвилинах. Інші технічні правила фіксовані всередині.
- Додано діагностику середнього сонячного балансу. Демо не надсилає команд кондиціонеру чи інвертору.

Актуальні правила та приклади: [docs/demo-strategy.md](docs/demo-strategy.md). Розділи про старі версії вище описують попередні етапи; поточний інтерфейс відповідає 0.2.5.
